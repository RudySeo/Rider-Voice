# Rider Voice UI/UX 디자인 가이드

## 먼저 보는 사용자 경험

이 문서는 화면을 예쁘게 만드는 규칙만 다루지 않습니다. 사용자가 Rider Voice를 처음 열어 정보를 찾고, 리뷰를 작성하고, 서비스의 한계를 이해하는 전 과정을 설명합니다.

### 사용자가 경험하는 기본 흐름

```text
앱 실행
  ▼
음식점 이름 또는 주소 검색
  ▼
검색 결과 선택
  ▼
음식점의 항목별 결과와 개별 리뷰 확인
  ├── 조회만 할 때: 로그인 없이 계속
  └── 리뷰를 쓸 때: 카카오 로그인 후 작성 화면으로 복귀
```

카카오에 없는 배달 브랜드는 주소를 검색해 실제 픽업 장소를 선택한 다음, 브랜드 정보와 첫 리뷰를 함께 등록합니다. 음식점 정보만 빈 상태로 먼저 저장하지 않습니다.

### 화면을 검토할 때 확인할 것

| 질문 | 올바른 화면의 기준 |
| --- | --- |
| 로그인하지 않아도 사용할 수 있는가? | 검색, 음식점 상세와 공개 리뷰는 로그인 없이 볼 수 있어야 합니다. |
| 무엇이 확인되지 않았는지 알 수 있는가? | 작성자의 신분과 실제 방문이 인증되지 않았다는 안내가 보여야 합니다. |
| 리뷰가 적을 때 오해하지 않는가? | 작성자 1~4명일 때는 결과 대신 `리뷰 수집 중` 상태를 보여야 합니다. |
| 점수가 순위처럼 보이지 않는가? | 헬멧과 5점 환산값은 6개 항목 각각에만 사용해야 합니다. |
| 다음 행동을 찾을 수 있는가? | 결과 없음, 오류, 로그인 필요 상태마다 사용자가 할 수 있는 행동을 안내해야 합니다. |

화면별 목적과 문구를 확인하려면 3~5장을 읽고, 색상·글꼴·간격과 구현 기준이 필요한 디자인·개발 담당자는 6장 이후를 확인합니다.

## 1. 문서 목적

이 문서는 Rider Voice 모바일 앱의 현재 UI/UX 디자인 방향을 제품·디자인·개발이 함께 사용할 수 있도록 정리한다.

문서가 다루는 범위는 다음과 같다.

- 사용자와 제품 경험의 방향
- 정보 구조와 주요 사용자 흐름
- 화면별 목적, 정보 우선순위와 상태
- 컬러, 타이포그래피, 간격과 형태
- 공통 UI 컴포넌트와 상호작용
- 신뢰 안내, 평가 결과와 접근성 기준
- React Native 구현 시 유지해야 할 디자인 원칙

제품 정책과 기능 범위는 `PRD.md`, 시스템 구조는 `ARCHITECTURE.md`, 데이터 구조는 `ERD.md`, 기술적 결정 배경은 `ADR.md`를 기준으로 한다. 이 문서와 제품 정책이 충돌하면 제품 정책을 우선하고 디자인 문서를 함께 갱신한다.

현재 상태는 **네이티브 개발 빌드로 구현하는 모바일 앱의 디자인 기준**이다. iOS·Android application identifier는 `com.ridervoice.app`, 로그인 callback은 `ridervoice://auth/callback`으로 고정한다. Expo Go는 접근 가능한 API가 설정된 공개 조회와 UI 확인에 사용할 수 있지만 실제 로그인이나 리뷰 변경 성공을 흉내 내지 않는다. API가 없거나 연결되지 않으면 고정된 가짜 검색 결과로 대체하지 않고 설정·연결 오류를 표시한다. 실제 앱 구현과 사용성 검증을 거치며 수치와 세부 동작은 조정할 수 있다.

## 2. 제품 경험의 방향

### 2.1 한 문장 정의

> 주문하기 전에 음식점의 준비 상태, 포장과 픽업 환경을 미리 확인하는 매장 운영 경험 서비스

Rider Voice는 배달 라이더만을 위한 작업 도구처럼 보이지 않아야 한다. 소비자가 음식점을 다시 검색하고 주문 여부를 판단할 수 있는 공개 정보 서비스가 중심이며, 로그인 사용자는 자신이 관찰한 운영 경험을 작성할 수 있다.

### 2.2 핵심 사용자

| 사용자 | 주요 목적 | 로그인 필요 여부 |
| --- | --- | --- |
| 소비자 | 음식점 검색, 운영 경험과 개별 리뷰 확인 | 필요 없음 |
| 일반 사용자 | 카카오 로그인 후 공개 정보와 내 활동 확인, 라이더 권한 인증 | 필요 |
| 라이더 권한 사용자 | 구조화된 운영 경험 작성·수정·관리 | 필요 |
| 관리자 | 신고 확인과 음식점 정보 정정 | 별도 관리 화면 |

카카오 로그인으로 생성된 사용자는 `USER`이며, 운영자가 별도로 전달한 공유 인증번호를 입력하면 `RIDER`로 승격된다. 이 번호는 내부 리뷰 작성 권한을 부여하는 수단일 뿐 작성자의 신원, 특정 직업 또는 개별 방문 사실을 공개적으로 보증하지 않는다. 공개 화면에는 인증 상태나 인증 배지를 노출하지 않는다.

### 2.3 UX 원칙

1. **검색이 첫 행동이다.** 홈 화면의 가장 강한 행동은 음식점명 또는 주소 검색이다.
2. **로그인 전에도 가치를 제공한다.** 검색, 음식점 상세와 공개 리뷰는 로그인 없이 이용할 수 있다.
3. **결론보다 근거를 보여준다.** 음식점 종합 순위 대신 항목별 결과, 작성자 수와 개별 경험을 보여준다.
4. **권한과 공개 사실을 구분한다.** 내부 작성 권한을 공개 리뷰의 사실 보증이나 인증 배지로 표현하지 않는다.
5. **작성 부담을 낮춘다.** 리뷰는 명확한 선택지와 선택 의견으로 구성하고, 한 화면에서 한 가지 판단에 집중한다.
6. **색상만으로 의미를 전달하지 않는다.** 텍스트, 아이콘, 개수와 상태명을 함께 사용한다.
7. **친근하지만 가볍지 않다.** 파스텔 보조색으로 경직된 느낌을 줄이되 데이터와 신뢰 안내는 차분하게 표현한다.

## 3. 정보 구조

### 3.1 하단 내비게이션

하단 내비게이션은 권한에 따라 두 항목 또는 세 항목을 제공한다.

| 탭 | 목적 | 비로그인 동작 |
| --- | --- | --- |
| 홈 | 음식점 검색과 공개 정보 탐색 | 바로 이용 |
| 리뷰 작성 | `RIDER`·`ADMIN`의 새 리뷰 작성 또는 기존 리뷰 진입 | 비로그인·`USER`에게 숨김 |
| 내 활동 | 작성한 리뷰와 공개 상태 확인 | 로그인 화면으로 이동 |

활성 탭은 딥 제이드 컬러와 굵은 레이블로 표시한다. 아이콘만으로 상태를 구분하지 않는다.

### 3.2 화면 구성

```text
홈
├── 검색 결과
│   ├── 리뷰가 있는 음식점
│   │   └── 음식점 상세
│   │       ├── 개별 경험 전체 보기
│   │       └── 라이더 권한 사용자에게만 리뷰 작성
│   └── 카카오에서 찾은 장소
│       └── 라이더 권한 사용자에게만 첫 리뷰 작성
├── 로그인
│   └── 내 활동으로 복귀
├── 리뷰 작성
│   └── 작성 완료
└── 내 활동
    ├── USER의 라이더 권한 인증
    └── 작성 리뷰 상세·수정·삭제
```

## 4. 주요 사용자 흐름

### 4.1 소비자의 음식점 탐색

```text
홈에서 음식점명 또는 주소 입력
  -> 검색 결과 확인
  -> 리뷰가 있는 음식점 선택
  -> 항목별 결과와 작성자 수 확인
  -> 개별 경험 확인
  -> 주문 판단 또는 다른 음식점 검색
```

검색 결과는 내부 리뷰 데이터가 있는 음식점과 카카오에서 찾은 장소를 명확히 분리한다.

- `리뷰가 있는 음식점`: 내부 음식점 ID와 공개 경험이 있는 결과
- `카카오에서 찾은 장소`: 외부 검색 후보이며 아직 등록된 리뷰가 없는 장소

리뷰가 없는 카카오 장소의 첫 리뷰 작성과 직접 등록 행동은 `RIDER`·`ADMIN`에게만 제공한다.

```text
리뷰가 없는 카카오 장소 선택
  -> RIDER 또는 ADMIN 권한 확인
  -> 장소와 음식점명 확인
  -> 첫 리뷰 작성과 음식점 등록
```

리뷰 제출 시 서버는 앱이 보낸 이름과 주소를 그대로 저장하지 않고 카카오 장소 ID를 다시 조회해 장소를 확인한 뒤 음식점 등록과 첫 리뷰 생성을 한 트랜잭션으로 처리한다. 등록된 개별 리뷰가 있지만 작성자가 5명 미만인 음식점은 상세 화면에서 공개 리뷰를 보여주고 항목별 집계만 `리뷰 수집 중`으로 표시한다.

앱은 카카오 API를 직접 호출하지 않는다. 앱이 Spring Boot 검색 API를 한 번 호출하면 서버가 내부 데이터와 카카오 검색 결과를 합쳐 반환한다.

카카오 검색에 없는 배달 브랜드는 다음 흐름으로 이어진다.

```text
검색 결과의 직접 등록 선택
  -> RIDER 또는 ADMIN 권한 확인
  -> 서버 주소 검색
  -> 실제 픽업 장소 선택
  -> 배달 브랜드명·상세 주소·배달 앱 입력
  -> 리뷰 작성
  -> 서버 재검증 후 음식점 등록과 첫 리뷰 생성
```

기존 픽업 장소가 검색되면 새 장소를 만들지 않고 그 장소에 브랜드만 연결한다. 새 주소 후보를 선택한 경우에도 앱이 좌표를 저장 요청에 넣지 않으며, 원 주소 검색어와 선택한 표준 주소를 보내 서버가 같은 검색을 반복해 검증한다. 직접 등록 화면에서는 음식점만 미리 저장하지 않는다.

### 4.2 리뷰 작성

```text
음식점 상세 또는 리뷰 작성 탭
  -> RIDER 또는 ADMIN 권한 확인
  -> 음식점과 방문 연월 확인
  -> 6개 평가 항목 입력
  -> 선택 의견 입력
  -> 공개 전 안내 확인
  -> 등록 완료
```

리뷰 작성은 한 화면에 모든 항목을 밀집시키기보다 항목별 진행을 사용한다. 현재 앱은 여섯 항목을 한 단계씩 입력하고 마지막 단계에서 선택 의견을 받는다.

### 4.3 내 활동

```text
내 활동 탭
  -> USER는 6자리 인증번호 입력 후 RIDER로 승격
  -> RIDER·ADMIN은 새 리뷰 작성 행동 확인
  -> 전체 작성 수와 공개 수 확인
  -> 최근 작성 목록 확인
  -> 리뷰 선택
  -> 공개 상태 확인 또는 수정·삭제
```

`공개됨`, `의견 숨김`, `리뷰 제외` 같은 상태는 색상뿐 아니라 텍스트로 표시한다.

## 5. 화면별 디자인 명세

### 5.1 홈

#### 목적

첫 방문자가 서비스의 가치를 이해하고 즉시 음식점을 검색하게 한다.

#### 정보 우선순위

1. 브랜드와 내 활동 진입
2. 핵심 질문: `주문 전, 이 음식점 어떤가요?`
3. 보조 설명: 준비 상태, 포장과 픽업 환경을 미리 확인할 수 있다는 가치
4. 음식점명 또는 주소 검색
5. 검색 후 확인할 수 있는 세 가지 정보

#### 정보 소개 항목

- 주문 준비가 안정적인가요?
- 포장은 깔끔하게 전달되나요?
- 픽업 공간과 응대는 어떤가요?

세 항목은 각각 살구색, 라벤더색, 민트색 아이콘 배경을 사용한다. 행 전체를 눌러 검색 입력으로 초점을 이동할 수 있다.

마지막 안내 문구는 `이용자가 남긴 매장 운영 경험`으로 표현한다. 내부 라이더 권한을 공개적인 신원·방문 보증으로 표현하지 않는다.

#### 레이아웃 기준

- 화면 좌우 기본 여백: 22dp
- 상단 브랜드 영역 뒤 충분한 호흡 공간 유지
- 검색 영역은 연한 제이드 배경 안에 입력창과 `확인하기` 버튼 배치
- 하단 목록 뒤에 의도적인 여백을 두되 빈 화면처럼 보이지 않도록 내비게이션까지의 간격을 일정하게 유지

### 5.2 검색 결과

#### 목적

리뷰가 있는 음식점과 아직 정보가 충분하지 않은 카카오 장소를 빠르게 구분한다.

#### 구성

1. 뒤로가기와 `검색 결과` 제목
2. 검색어 수정 필드와 `검색` 버튼
3. 검색어 요약
4. `리뷰가 있는 음식점`
5. `등록된 음식점`
6. `카카오에서 찾은 장소`
7. `찾는 배달 브랜드가 없나요?` 직접 등록 행동

#### 결과 행

리뷰가 있는 결과는 다음 정보를 제공한다.

- 음식점명
- 도로명 주소
- `N명의 경험`
- 상세 진입 표시

리뷰가 있는 결과에는 제이드 대신 **퍼리윙클 계열**을 사용해 검색 버튼과 시각적으로 경쟁하지 않게 한다.

- 아이콘·개수 배지 배경: 연한 퍼리윙클
- 경험 수 텍스트: 짙은 퍼리윙클
- 선택과 이동은 행 전체 터치

카카오 장소는 회색 위치 아이콘을 사용한다. `RIDER`·`ADMIN`에게만 `첫 리뷰 작성` 상태와 작성 흐름을 제공하고 그 외 사용자에게는 작성 행동을 노출하지 않는다.

검색 성공 후에는 결과가 0개여도 `RIDER`·`ADMIN`에게 직접 등록 행동을 제공한다. 이 행동은 주소 검증 화면으로 이동하며, 검색 장애 상태에서 주소 provider 검증까지 실패하면 등록할 수 없다는 오류와 재시도 행동을 보여준다.

MVP 검색 API는 사용자 위치와 거리 정보를 받거나 반환하지 않는다. 따라서 검색 결과에서 `가까운 순`, 미터 단위 거리와 위치 권한 요청을 제공하지 않는다. 결과 순서는 서버가 반환한 통합 검색 순서를 그대로 사용한다. 위치 기반 검색이 필요해지면 요청 좌표, 거리 계산 주체, 정렬과 위치 거부 상태를 별도 API 계약으로 정의한다.

#### 상태

| 상태 | 화면 표현 |
| --- | --- |
| 로딩 | 결과 행 형태의 스켈레톤과 검색 필드 유지 |
| 결과 없음 | 검색어를 다시 확인하도록 안내하고 새 검색 행동 제공 |
| 내부 결과만 가능 | 카카오 검색을 사용할 수 없다는 인라인 안내 표시 |
| 리뷰 0명인 카카오 장소 | `RIDER`·`ADMIN`에게만 `첫 리뷰 작성` 표시와 작성 이동 제공 |
| 리뷰 1~4명 | `리뷰 수집 중 · N명` 표시, 항목별 집계는 숨김 |
| 리뷰 5명 이상 | `N명의 경험` 표시, 상세에서 항목별 결과 제공 |

### 5.3 카카오에 없는 브랜드 직접 등록

#### 목적

사용자가 임의 좌표나 장소 정보를 저장하지 못하게 하면서 실제 픽업 장소와 소비자에게 보이는 배달 브랜드를 구분해 입력하게 한다.

#### 구성과 상태

1. 원 검색어가 채워진 주소 검색 필드
2. 표준 주소·지번 주소와 기존 픽업 장소 여부가 표시된 후보 목록
3. 소비자에게 보이는 배달 브랜드명
4. 새 픽업 장소일 때만 표시하는 선택 상세 주소
5. 선택 가능한 배달 앱 목록
6. `리뷰 작성으로 계속` 행동

로딩, 결과 없음, provider 오류와 재시도 상태를 화면 안에서 구분한다. 주소 후보를 고르기 전에는 브랜드 입력을 노출하지 않고, 기존 픽업 장소를 고르면 상세 주소를 다시 받지 않는다. 배달 앱은 선택 사항이며 브랜드명은 필수다.

### 5.4 음식점 상세

#### 목적

소비자가 음식점의 운영 경험을 항목별로 이해하고, 결과의 근거와 한계를 함께 확인하게 한다.

#### 정보 우선순위

1. 음식점명
2. 배달 앱 표시 가게인지 실제 픽업 장소인지에 대한 맥락
3. 실제 픽업 주소
4. 항목별 결과와 작성자 수
5. 개별 경험
6. `RIDER`·`ADMIN`에게만 리뷰 작성 행동

#### 항목 그룹

| 그룹 | 평가 항목 |
| --- | --- |
| 배달 준비 | 포장 안정성, 주문 준비 상태, 주문 확인·전달 정확성 |
| 픽업 환경 | 픽업 공간 청결, 직원 응대, 라이더 존중 |

각 그룹에는 서로 다른 유효 작성자 수를 표시한다. 그룹은 접고 펼칠 수 있지만 첫 방문에서는 핵심 그룹 하나 이상을 펼친 상태로 보여준다.

#### 헬멧 평가 표현

별 대신 **풀페이스 라이더 헬멧 아이콘**을 사용한다. 헬멧은 브랜드 장식이 아니라 항목별 운영 경험을 빠르게 읽기 위한 시각화다.

- 활성 헬멧: 따뜻한 앰버
- 비활성 헬멧: 웜 그레이
- 아이콘 배경: 매우 연한 앰버
- 보조 문구: `헬멧이 많을수록 원활한 운영 경험이에요`
- `관찰하지 못함` 인원은 헬멧 채움에서 제외하고 별도 텍스트로 표시
- 음식점 전체를 하나의 점수로 평가하거나 순위를 만들지 않음

항목별 결과는 `3.8 / 5`처럼 5점 환산 점수와 헬멧 다섯 개로 표시한다. 음식점 전체 점수는 만들지 않고 6개 평가 항목에만 각각 적용한다.

원래 응답 네 단계는 동일한 간격으로 계산한다.

| 응답 | 원점수 |
| --- | ---: |
| 매우 좋음 | 4 |
| 좋음 | 3 |
| 개선 필요 | 2 |
| 큰 개선 필요 | 1 |
| 관찰하지 못함 | 계산 제외 |

```text
4단계 평균 =
  (매우 좋음 수 × 4
   + 좋음 수 × 3
   + 개선 필요 수 × 2
   + 큰 개선 필요 수 × 1)
  ÷ 관찰 응답 수

5점 환산 점수 = 1 + (4단계 평균 - 1) × 4 ÷ 3
```

이 공식은 `큰 개선 필요`를 1.0, `매우 좋음`을 5.0으로 두고 네 응답 사이의 간격을 동일하게 유지한다. 점수는 서버에서만 계산하고 앱은 API가 반환한 값을 표시한다.

- 서버 계산 중간값은 반올림하지 않음
- API의 `score`는 소수점 첫째 자리로 반환
- `관찰하지 못함`은 분모와 점수 계산에서 제외하고 인원수만 별도 공개
- 관찰 응답이 0명이면 `score`는 `null`이며 헬멧 대신 `관찰된 응답 없음` 표시
- 서로 다른 유효 작성자 5명 미만이면 `score`와 응답 분포를 공개하지 않음
- 점수가 공개되면 응답 분포를 함께 제공해 같은 평균 안의 의견 차이를 확인할 수 있게 함
- 앱에서 범주별 분포를 사용해 점수를 다시 계산하거나 보정하지 않음

헬멧 채움은 점수에 맞춰 왼쪽부터 표현하며 마지막 헬멧은 부분 채움을 지원한다. 시각화만으로 값을 판단하지 않도록 숫자 점수, 관찰 응답 수와 `관찰하지 못함` 인원수를 함께 표시한다.

#### 공개 기준

- 서로 다른 유효 작성자 5명 이상: 항목별 결과 공개
- 1~4명: 현재 작성자 수와 수집 중 상태만 표시
- 0명: 첫 경험 작성 행동 제공
- 삭제 또는 제외로 다시 5명 미만이 되면 결과를 다시 숨김

### 5.5 개별 경험

개별 경험은 통계 아래에 배치해 결과의 실제 맥락을 보완한다.

각 항목은 다음 정보를 포함한다.

- 최대 200자의 자유 의견
- 방문 연월
- 작성 후 경과 시간
- 공개 또는 숨김 상태가 필요한 경우 상태명

작성자의 이름, 프로필 사진과 고정 공개 ID는 표시하지 않는다.

### 5.6 로그인

#### 목적

로그인 장벽을 낮추면서 카카오 로그인의 의미와 한계를 정확히 설명한다.

#### 원칙

- 사용자가 내 활동을 선택했을 때 로그인 요청
- 상단에 사용자가 계속하려던 목적 표시
- 검색과 공개 정보는 로그인 없이 이용 가능하다고 안내
- 작성자 이름과 프로필이 공개되지 않는다고 안내
- 카카오 로그인은 계정 식별 수단이고 리뷰 작성에는 별도 라이더 권한이 필요하다고 명시
- `카카오로 계속하기`와 `나중에 하기`를 함께 제공
- 로그인 성공 후 홈이 아니라 원래 목적 화면으로 복귀

카카오 버튼은 카카오 브랜드 가이드에 맞는 노란색을 사용하고 앱의 제이드 버튼으로 임의 변경하지 않는다.

### 5.7 리뷰 작성

#### 선택지

- 매우 좋음 — 기대보다 훨씬 원활했어요
- 좋음 — 대체로 원활했어요
- 개선 필요 — 불편한 점이 있었어요
- 큰 개선 필요 — 중요한 개선이 필요해요
- 관찰하지 못함 — 확인하지 않은 항목이에요

#### 상호작용

- 선택 행 전체를 터치 가능하게 구성
- 선택 상태는 제이드 테두리, 연한 제이드 배경과 채워진 라디오 표시를 함께 사용
- `관찰하지 못함`은 중립 배경을 사용하되 다른 선택지와 동일한 접근성 제공
- 필수 항목을 선택하기 전 등록 버튼 비활성화
- 의견은 선택 사항이며 최대 글자 수와 남은 글자 수 제공
- 키보드가 버튼이나 입력 항목을 가리지 않도록 화면을 조정
- 등록 성공 후 완료 상태와 `내 활동 보기` 행동 제공

### 5.8 내 활동

#### 구성

- 페이지 제목과 설명
- 작성한 리뷰 수
- 현재 공개된 리뷰 수
- 최근 작성 목록
- `USER`: 6자리 라이더 권한 인증번호 입력과 실패·잠금 상태
- `RIDER`·`ADMIN`: 새 리뷰 작성 행동

리뷰 행에는 음식점명, 대표 평가 항목과 선택값, 작성 시점, 공개 상태를 표시한다. 수정·삭제는 리뷰 상세 화면에서 제공하고 파괴적 행동은 확인 절차를 거친다.

### 6.2 타이포그래피

기본 서체는 `LINE Seed Sans KR`을 사용한다. 공식 안내에 따르면 LINE Seed는 SIL Open Font License 1.1로 배포되어 개인·상업 목적 모두 사용할 수 있으므로 유료 앱과 상업 서비스에도 사용할 수 있다.

- 공식 라이선스 안내: <https://seed.line.me/>
- SIL Open Font License 1.1: <https://openfontlicense.org/>
- 폰트 파일 자체를 별도 상품으로 판매하지 않음
- 앱 저장소에 원본 라이선스 파일을 함께 보관
- 앱 또는 서비스의 오픈소스 고지 화면에 `LINE Seed KR · LY Corp. · SIL OFL 1.1` 출처 표기
- 폰트 파일은 확인된 공식 배포본을 앱에 직접 포함하고 임의 CDN에 의존하지 않음

대체 서체인 `Pretendard`와 `Noto Sans KR`도 SIL OFL 1.1 배포본만 사용한다. 사용할 수 없는 환경에서는 다음 순서로 대체한다.

```text
LINE Seed Sans KR
Pretendard
Noto Sans KR
system sans-serif
```

### 6.3 간격과 그리드

기본 간격은 4dp 배수를 사용한다.

```text
4, 8, 12, 16, 20, 24, 28, 32
```

- 화면 좌우 여백: 22dp
- 화면 상단 콘텐츠 여백: 헤더가 없으면 약 58dp, 헤더가 있으면 약 24dp
- 목록 행 세로 여백: 12~17dp
- 섹션 사이 간격: 22~28dp
- 텍스트와 보조 설명 간격: 3~8dp
- 하단 내비게이션이 있는 화면은 안전 영역과 내비게이션 높이를 포함한 하단 여백 확보

빈 공간은 장식으로 채우지 않는다. 다만 마지막 목록과 하단 내비게이션 사이가 끊어진 화면처럼 보이지 않도록 일관된 최소 하단 여백을 유지한다.

| --- | ---: |
| 입력창·기본 버튼 | 14dp |
| 검색 패널 | 18dp |
| 카테고리 아이콘 배경 | 13~14dp |
| 정보 배너 | 14dp, 홈 전체 폭 배너는 0dp |
| 통계 카드 | 16dp |
| 큰 상태 아이콘 | 20~22dp |

그림자는 최소화하고 표면 구분은 배경색, 1dp 테두리와 간격을 우선한다.

### 6.5 아이콘

- 기본 아이콘은 1.5~2dp 선 굵기의 단순한 라인 아이콘 사용
- 아이콘 기본 크기: 20~22dp
- 뒤로가기, 검색, 홈, 리뷰 작성, 사용자, 위치, 정보 아이콘의 스타일 통일
- 헬멧은 풀페이스 형태의 전용 SVG 사용
- 이모지 또는 서로 다른 스타일의 아이콘 혼용 금지
- 의미가 불명확한 아이콘 버튼에는 접근성 레이블 필수

## 7. 공통 컴포넌트

React Native 구현에서는 다음 컴포넌트를 우선 공통화한다.

| 컴포넌트 | 책임 |
| --- | --- |
| `Screen` | 안전 영역, 배경과 기본 좌우 여백 |
| `AppText` | 서체, 역할별 크기와 글꼴 확대 정책 |
| `ScreenHeader` | 뒤로가기, 제목과 선택 행동 |
| `BottomTabBar` | 권한에 따른 홈·리뷰 작성·내 활동 이동 |
| `SearchField` | 검색 아이콘, 입력과 제출 상태 |
| `PrimaryButton` | 주요 행동, 비활성·로딩·눌림 상태 |
| `CategoryIcon` | 살구·라벤더·민트 카테고리 아이콘 |
| `RestaurantRow` | 음식점명, 주소, 경험 수 또는 첫 리뷰 작성 상태 |
| `StatusBadge` | 수집 중, 공개됨, 숨김 등 상태 |
| `HelmetRating` | 항목별 헬멧 시각화와 접근성 설명 |

컴포넌트는 시각 상태뿐 아니라 `default`, `pressed`, `focused`, `disabled`, `loading`, `error` 상태를 정의한다.

## 8. 접근성

### 8.1 터치와 초점

- 주요 터치 영역은 최소 44×44dp 확보
- 텍스트 링크도 주변 여백을 포함해 충분한 터치 영역 제공
- 행 전체가 이동 행동이면 중첩된 작은 이동 버튼을 만들지 않음
- 키보드와 스크린 리더 탐색 순서는 시각 순서와 일치
- 포커스 표시를 제거하지 않음

### 8.2 텍스트와 색상

- 일반 텍스트는 배경과 WCAG AA 수준 대비 확보
- 작은 회색 텍스트는 실제 기기에서 대비 확인
- 상태는 색상 외에 레이블과 아이콘을 함께 제공
- 시스템 글꼴 확대에서 버튼과 행 높이가 콘텐츠에 맞게 늘어나도록 구현
- 중요한 설명을 한 줄 고정 또는 말줄임으로 숨기지 않음

### 8.3 스크린 리더

헬멧 아이콘 각각을 읽게 하지 않고 묶음 전체를 하나의 의미로 제공한다.

예시:

```text
포장 안정성, 서로 다른 작성자 7명 평가,
관찰하지 못함 1명, 항목별 결과 5단계 중 3.8
```

점수와 함께 실제 범주별 응답 분포를 펼쳐 볼 수 있으며, 분포 영역은 각 범주와 응답 비율 또는 인원수를 순서대로 읽는다.

### 8.4 모션

- 화면 전환과 선택 피드백은 짧고 기능적인 애니메이션만 사용
- 시스템의 `동작 줄이기` 설정을 존중
- 로딩 중 반복 애니메이션은 정보를 가리지 않음

## 9. 콘텐츠 작성 원칙

### 9.1 말투

- 존댓말 사용
- 사용자를 탓하지 않는 문장
- 법률·기술 용어 대신 짧고 쉬운 설명
- 확정할 수 없는 사실을 단정하지 않음

### 9.2 권장 표현

| 상황 | 권장 표현 |
| --- | --- |
| 검색 시작 | 음식점 이름 또는 주소 |
| 공개 기준 미달 | 리뷰를 모으고 있어요 · 현재 N명 |
| 리뷰 없음 | 아직 등록된 경험이 없어요 |
| 리뷰 없는 카카오 장소 | 아직 등록된 경험이 없어요. 첫 리뷰를 작성해 주세요. |
| 카카오 장애 | 카카오 장소 검색을 잠시 사용할 수 없어요. 등록된 음식점 결과만 보여드려요. |
| 로그인 유도 | 로그인하면 내 활동을 확인할 수 있어요 |
| 권한 안내 | 리뷰 작성에는 라이더 권한이 필요해요 |

`인증 리뷰`, `검증된 라이더`, `믿을 수 있는 방문`처럼 실제 정책보다 강한 신뢰를 암시하는 표현은 사용하지 않는다.

## 10. 네이티브 앱 구현 기준

- iOS와 Android의 안전 영역을 적용한다.
- 하단 내비게이션은 홈 인디케이터와 Android 시스템 내비게이션을 침범하지 않는다.
- 키보드가 검색 제출 버튼, 리뷰 입력과 등록 버튼을 가리지 않는다.
- 기기 너비가 달라도 고정된 휴대폰 프레임 폭을 기준으로 축소하지 않고 실제 화면 너비에 맞춰 재배치한다.
- 큰 UI 라이브러리의 기본 테마보다 이 문서의 디자인 토큰과 공통 컴포넌트를 우선한다.
- 목록 데이터는 TanStack Query 상태와 연결하되 로딩·오류 시 기존 검색어와 화면 맥락을 유지한다.
- API의 작성자 수, 공개 상태와 `NOT_OBSERVED` 값을 임의로 숨기거나 추정하지 않는다.

## 11. 사용성 검증 항목

실제 앱 구현 후 다음 질문을 기준으로 테스트한다.

1. 첫 방문자가 5초 안에 앱이 제공하는 정보를 설명할 수 있는가?
2. 로그인 없이 검색과 상세 조회가 가능하다는 사실을 이해하는가?
3. 검색 결과에서 리뷰가 있는 음식점과 카카오 장소를 구분하는가?
4. 헬멧이 음식점 종합 순위가 아니라 항목별 결과라는 점을 이해하는가?
5. `USER`가 내 활동에서 인증번호를 입력해 권한 변경을 확인할 수 있는가?
6. 비로그인·`USER`에게 리뷰 작성 행동이 노출되지 않는가?
7. 리뷰 작성자가 `관찰하지 못함`을 부담 없이 선택할 수 있는가?
8. 글꼴 확대, 스크린 리더와 동작 줄이기 환경에서 핵심 흐름을 완료할 수 있는가?
9. 카카오 검색 장애, 결과 없음과 리뷰 5명 미만 상태에서 다음 행동을 찾을 수 있는가?
10. 카카오에 없는 브랜드를 직접 등록할 때 픽업 장소와 배달 브랜드가 다른 정보라는 점을 이해하는가?
