# PRD: Rider Voice 공개 리뷰 MVP

## 1. 제품 개요

Rider Voice는 픽업 과정에서 관찰한 음식점 운영 환경을 카카오 로그인 사용자가 구조화된 리뷰로 공유하고, 소비자 누구나 그 정보를 확인할 수 있는 서비스다.

초기 MVP에서는 라이더 신분과 실제 방문을 인증하지 않는다. 카카오 로그인은 서비스 계정을 식별하기 위한 수단이며 작성자의 직업이나 방문 사실을 증명하지 않는다. 서비스와 공개 응답은 이 한계를 명확히 알리고 리뷰를 인증된 정보로 표현하지 않는다.

배달내역 화면 캡처, 이미지 업로드, OCR 또는 배달 앱 화면 파싱은 사용하지 않는다. 인증은 운영 데이터에서 실제 필요성이 확인되고 낮은 마찰의 수단이 생겼을 때 별도 검토한다.

## 2. 해결하려는 문제

- 일반 음식점 리뷰는 맛과 소비자 경험 중심이어서 픽업 공간, 준비 상태와 라이더 응대 같은 운영 환경을 알기 어렵다.
- 배달 플랫폼에 등록된 상호와 실제 픽업 장소가 다르거나 한 장소에서 여러 배달 브랜드를 운영하는 경우가 있다.
- 라이더가 알고 있는 현장 정보를 소비자가 확인할 수 있는 구조화된 공개 채널이 부족하다.
- 초기부터 복잡한 방문 인증을 요구하면 작은 사용자 기반에서 작성 전환을 크게 낮출 수 있다.

## 3. 사용자와 신뢰 원칙

- **소비자**: 로그인 없이 음식점을 검색하고 개별 리뷰와 공개 가능한 집계를 확인한다.
- **작성자**: 카카오 로그인과 필수 약관 동의를 완료한 활성 사용자다. 별도 라이더·방문 인증 없이 리뷰를 작성한다.
- **관리자**: 자유 의견 검수, 신고 처리, 잘못된 음식점 연결과 중복을 정정한다.

모든 공개 리뷰와 리포트에는 다음 의미의 안내를 제공한다.

> 이 정보는 카카오 로그인 사용자가 작성했으며 라이더 신분과 실제 방문 여부는 인증되지 않았습니다. 5명 집계는 서로 다른 서비스 계정을 기준으로 합니다.

5명 기준은 표본 공개 기준일 뿐 방문 인증이나 사실 보증이 아니다. 종합 별점, 음식점 순위와 인증 배지를 제공하지 않는다.

## 4. 핵심 사용자 흐름

### 4.1 카카오 로그인

1. 사용자가 Spring Security OAuth2 Client가 제공하는 카카오 로그인 흐름을 시작한다.
2. 카카오 callback에서 외부 계정의 고유 식별자를 확인한다.
3. 서버는 service token 대신 60초 동안 한 번만 사용할 수 있는 교환 코드를 고정된 frontend callback URL에 전달한다.
4. 웹 클라이언트는 교환 코드를 API에 제출해 약관 상태에 따라 onboarding token 또는 Rider Voice access token과 rotating refresh token을 받는다.
5. 신규 사용자는 onboarding token으로 필수 약관에 동의한다.

OAuth 과정의 임시 session은 로그인 완료 후 폐기하고 REST API는 opaque bearer token으로 인증한다. onboarding token, access token과 refresh token은 URL query string이나 fragment에 포함하지 않는다.

### 4.2 음식점 검색

1. 소비자가 음식점명 또는 주소를 검색한다.
2. 서버는 내부 배달 브랜드와 카카오 장소 후보를 병합한다.
3. 내부에 리뷰가 없는 카카오 후보도 `NO_REVIEWS` 상태로 보여준다.
4. 카카오 검색이 일시적으로 실패하면 이미 등록된 내부 음식점 결과만 제공하고 외부 검색 제한 상태를 표시한다.

카카오 API는 서버에서만 호출하며 카카오 장소 ID만으로 내부 음식점을 생성하지 않는다.

### 4.3 첫 리뷰와 음식점 지연 등록

작성자는 리뷰 작성 시 다음 중 하나를 선택한다.

1. 이미 등록된 배달 브랜드
2. 카카오 검색 결과의 장소
3. 이미 등록된 픽업 장소에 새 배달 브랜드 추가
4. 주소 검색으로 픽업 장소와 배달 브랜드를 함께 수동 등록

카카오 장소나 주소를 선택한 경우 서버가 원 검색어로 provider 검색을 반복해 선택 결과를 검증한다. 검증된 픽업 장소·배달 브랜드 등록과 첫 리뷰 생성은 하나의 use case로 처리한다.

### 4.4 공개 리뷰 작성

1. 작성자는 방문 연월과 6개 구조화 평가를 모두 선택한다.
2. 최대 200자의 선택 의견을 입력할 수 있다.
3. 구조화 평가는 작성 직후 공개된다.
4. 의견은 관리자 검수 후 공개된다.
5. 같은 음식점에는 마지막 제출 시각부터 90일 후 새 리뷰를 작성할 수 있다.
6. 새 리뷰가 생기면 이전 리뷰는 공개 이력으로 남지만 더 이상 수정할 수 없다.

### 4.5 소비자 조회와 집계

- 개별 리뷰는 유효한 첫 리뷰부터 공개한다.
- 음식점 브랜드 집계와 픽업 장소 집계는 각각 서로 다른 유효 작성자 5명부터 공개한다.
- 집계 전에는 `COLLECTING` 상태와 현재 작성자 수를 표시한다.
- 리뷰 삭제나 관리자 제외로 작성자 수가 5명 미만이 되면 다시 `COLLECTING`으로 전환한다.

### 4.6 관리자 조사와 정정

1. 관리자는 검수·신고 대상 리뷰의 구조화 평가, 비공개 의견, 음식점과 작성자 활동 정보를 함께 확인한다.
2. 음식점 신고는 기각하거나 실제 이름·픽업 장소·중복·폐업 정정과 함께 승인한다.
3. 신고 승인, 실제 데이터 변경과 감사 기록은 하나의 트랜잭션에서 함께 완료한다.
4. 신고 없이 발견한 오류도 같은 검증과 감사 규칙으로 선제 정정할 수 있다.

### 4.7 임시 웹 클라이언트

로컬 사용자 흐름을 검증하기 위해 `/frontend`의 React SPA를 제공한다. 이 클라이언트는 현재 서버 API 계약을 브라우저에서 확인하는 prototype이며 별도 운영 제품이나 배포 대상이 아니다.

- 로그인하지 않은 사용자는 음식점을 검색하고 상세, 공개 리뷰와 브랜드·픽업 장소 리포트를 조회한다.
- 사용자는 카카오 로그인 callback의 교환 코드를 처리하고, 필요한 경우 필수 약관에 동의한다.
- 활성 사용자는 `EXISTING`, `KAKAO`, `MANUAL_EXISTING_LOCATION`, `MANUAL_ADDRESS` 네 가지 음식점 target으로 리뷰를 작성한다.
- 활성 사용자는 내 리뷰 목록에서 현재 리뷰를 수정하거나 삭제한다.
- 모든 공개 리뷰와 리포트 화면은 `UNVERIFIED` 상태와 미인증 안내를 누락 없이 표시한다.

관리자·신고 UI와 실제 카카오 계정을 사용하는 브라우저 E2E는 이 prototype 범위에 포함하지 않는다. 카카오 OAuth redirect와 provider 연동은 서버 테스트와 수동 로컬 확인의 경계를 유지한다.

## 5. 음식점 모델

### 픽업 장소

`PickupLocation`은 실제로 음식을 받는 물리적 장소다.

- 표준 주소
- 정규화 주소
- 선택 상세 위치: 층, 호수, 픽업 입구 등
- 위도와 경도
- 등록 출처

표준 주소와 상세 위치를 정규화한 `locationKey`로 같은 픽업 장소의 중복을 줄인다.

### 배달 브랜드

`Restaurant`은 소비자와 배달 플랫폼에 보이는 상호다.

- 하나의 픽업 장소에 여러 배달 브랜드를 연결할 수 있다.
- 같은 브랜드라도 주소가 다르면 별도 음식점이다.
- 같은 픽업 장소의 같은 정규화 브랜드명은 중복 등록하지 않는다.
- 같은 장소에 연결된 다른 브랜드 목록은 소비자에게 공개하지 않는다.
- 상태는 `ACTIVE`, `CLOSED`, `MERGED`이며 폐업 음식점은 검색과 신규 리뷰에서 제외한다.
- 폐업 음식점의 직접 상세와 기존 리뷰 이력은 `CLOSED` 표시와 함께 유지한다.

### 외부 장소와 플랫폼

- 카카오 장소 ID는 배달 브랜드의 외부 검색 참조로 저장한다.
- 한 픽업 장소에 서로 다른 카카오 장소 ID를 가진 여러 브랜드를 연결할 수 있다.
- 배민, 쿠팡이츠, 요기요와 기타 플랫폼 정보는 선택 메타데이터다.
- 플랫폼 정보는 음식점의 동일성이나 운영 주체를 증명하지 않는다.

## 6. 리뷰 입력과 집계 규칙

### 평가 값

| API 값 | 화면 표시 |
| --- | --- |
| `VERY_GOOD` | 매우 좋음 |
| `GOOD` | 좋음 |
| `NEEDS_IMPROVEMENT` | 개선 필요 |
| `MAJOR_IMPROVEMENT` | 큰 개선 필요 |
| `NOT_OBSERVED` | 관찰하지 못함 |

### 평가 항목

배달 브랜드 집계 항목:

1. 포장 안정성
2. 주문 준비 상태
3. 주문 확인·전달 정확성

픽업 장소 집계 항목:

1. 픽업 공간 청결
2. 직원 응대
3. 라이더 존중

6개 항목은 모두 필수다. `NOT_OBSERVED`는 작성자 수와 별도 개수에는 포함하지만 평가 비율의 분모에서는 제외한다.

브랜드 집계는 작성자별 현재 리뷰 하나를 사용한다. 장소 집계는 한 작성자가 같은 장소의 여러 브랜드에 현재 리뷰를 가지고 있어도 그중 가장 최근 유효 리뷰 하나만 사용한다.

## 7. 수정·삭제·검수·신고

- 현재 리뷰만 수정하거나 삭제할 수 있다.
- 방문 연월은 수정할 수 없다.
- 최신 리뷰를 삭제해도 마지막 제출 시각은 남겨 90일 제한을 우회할 수 없게 한다.
- 최신 리뷰가 삭제되거나 전체 제외돼도 과거 리뷰를 현재 집계 대상으로 복원하지 않는다.
- 삭제는 리뷰 본문 hard delete이며 작성 제한 상태와 관리자 감사 기록은 유지한다.
- 의견을 수정하면 기존 공개 의견을 숨기고 다시 검수한다.
- 신고 접수 시 공개 의견만 임시 숨기고 구조화 평가는 유지한다.
- 신고가 허위·도배로 인정되면 리뷰 전체를 공개와 집계에서 제외한다.
- 리뷰 전체 제외 시 같은 리뷰의 다른 대기 신고는 대상 제외를 근거로 자동 종결한다.
- 잘못된 음식점 정보와 중복은 관리자 이름 변경·검증된 장소 재연결·폐업·재개장·병합으로 처리한다.
- 올바른 픽업 장소가 아직 없으면 서버가 주소 provider를 다시 검증한 뒤 새 장소 생성과 재연결을 함께 처리한다.
- 관리자 조치와 자동 종결은 조회 가능한 감사 이력에 남긴다.

## 8. MVP 범위

### 포함

- Spring Security OAuth2 Client 기반 카카오 로그인
- Rider Voice opaque access/refresh token과 약관 동의
- 공개 음식점 검색·상세·리뷰 조회
- 카카오 장소와 주소 검색
- 픽업 장소·배달 브랜드 분리 및 지연 등록
- 6개 평가, 방문 연월, 최대 200자 의견
- 90일 재작성과 공개 리뷰 이력
- 작성자 5명 기준 브랜드·장소 집계
- 의견 검수, 리뷰·음식점 신고와 관리자 처리
- 관리자 대상 상세·검색·감사 조회
- 음식점 이름·픽업 장소·폐업 정정, 중복 병합과 canonical 음식점 연결
- OpenAPI, 권한·유효성·동시성 테스트
- `/frontend` 로컬 React SPA에서 공개 검색·상세·리뷰 조회
- 웹 카카오 로그인 교환·약관 동의와 네 가지 target 리뷰 작성
- 웹 내 리뷰 조회·수정·삭제

### 제외

- 라이더 신분과 실제 방문 인증
- 배달내역 캡처·이미지 업로드·OCR·배달 앱 화면 파싱
- 종합 별점, 순위와 인증 배지
- 같은 픽업 장소의 다른 브랜드 공개
- 리워드와 서버 강제 지역 제한
- 운영용 웹·React Native 클라이언트와 frontend 배포
- 관리자·신고 UI
- 실제 카카오 계정을 사용하는 브라우저 E2E 자동화
- Redis, Kafka, Elasticsearch
- Docker, Testcontainers, AWS와 운영 배포

## 9. 완료 기준

- 소비자가 로그인 없이 내부 음식점과 카카오 후보를 검색할 수 있다.
- 활성 사용자가 기존·카카오·수동 음식점 대상으로 리뷰를 작성할 수 있다.
- 음식점 등록과 첫 리뷰 생성이 실패 시 함께 롤백된다.
- 최신 리뷰 수정·삭제와 90일 재작성 정책을 DB 상태와 application 정책으로 보장한다.
- 개별 리뷰는 즉시 공개되고 의견은 승인 후에만 공개된다.
- 브랜드와 장소 집계가 작성자 5명 기준 및 `NOT_OBSERVED` 규칙대로 동작한다.
- 신고 승인 시 허위·도배 리뷰가 공개와 집계에서 제외된다.
- 관리자에게 신고 판단에 필요한 대상 맥락이 제공된다.
- 음식점 신고 승인과 실제 정정 및 감사 기록이 함께 성공하거나 실패한다.
- 폐업 음식점은 검색·신규 작성에서 제외되고 기존 공개 이력은 유지된다.
- 모든 공개 응답이 미인증 상태를 명확히 전달한다.
- 공개·사용자·관리자 권한과 OpenAPI 계약이 테스트된다.
- 로컬 웹 prototype에서 공개 조회, OAuth 교환·약관 동의, 네 가지 target 리뷰 작성과 내 리뷰 수정·삭제 흐름을 실행할 수 있다.
