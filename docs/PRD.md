# PRD: Rider Voice 공개 리뷰 MVP

## 먼저 읽기

이 문서는 Rider Voice가 **누구의 어떤 문제를 해결하는지**, **현재 어떤 기능을 제공하는지**, **서비스가 반드시 지켜야 할 기준이 무엇인지** 설명합니다. 개발 방법보다 사용자 경험과 운영 정책을 이해하는 것이 목적입니다.

Rider Voice를 한 문장으로 설명하면 다음과 같습니다.

> 소비자가 음식점의 배달 준비와 픽업 환경을 미리 확인하고, Rider Voice의 `RIDER` 작성 권한을 얻은 사용자가 경험을 공유하는 서비스입니다.

서비스를 이해할 때는 다음 세 가지를 구분해야 합니다.

| 구분 | 의미 |
| --- | --- |
| 개별 리뷰 | 한 사람이 작성한 6개 평가와 선택적인 자유 의견이며 첫 리뷰부터 공개됩니다. |
| 집계 결과 | 여러 사람의 평가를 모은 항목별 결과이며 서로 다른 유효 작성자 5명부터 공개됩니다. |
| 로그인과 역할 | 카카오 로그인으로 계정을 구분하고 공용 인증번호로 리뷰 작성용 `RIDER` 역할을 부여합니다. |

세부 시스템 구조는 [ARCHITECTURE.md](ARCHITECTURE.md), 데이터 관계는 [ERD.md](ERD.md), 결정 배경은 [ADR.md](ADR.md), 화면 기준은 [design.md](design.md)에서 확인합니다.

## 1. 서비스 소개

Rider Voice는 음식점의 배달 준비와 픽업 환경에 대한 리뷰를 모아 보여주는 서비스입니다.

일반 음식점 리뷰에서는 음식의 맛이나 소비자 응대는 확인할 수 있지만, 포장이 안정적인지, 주문이 제때 준비되는지, 픽업 공간이 깨끗한지 같은 정보는 알기 어렵습니다. Rider Voice는 이런 정보를 정해진 항목으로 모아 소비자에게 제공합니다.

소비자는 로그인 없이 리뷰를 볼 수 있고, 카카오 로그인 후 공용 6자리 인증번호를 통과한 `RIDER`와 `ADMIN`은 리뷰를 작성할 수 있습니다.

## 2. 해결하려는 문제

- 소비자가 음식점의 배달 준비 상태나 픽업 환경을 미리 알기 어렵습니다.
- 배달 앱의 브랜드명과 실제 픽업 장소가 다르거나, 한 장소에서 여러 브랜드를 운영하는 경우가 있습니다.
- 현장에서 알게 된 정보를 일정한 기준으로 공유할 공개 공간이 부족합니다.
- 모든 로그인 계정에 작성 권한을 주면 리뷰 작성 주체를 운영하기 어렵습니다.

초기 MVP에서는 운영자가 관리하는 공용 인증번호로 작성자를 제한하고 실제로 리뷰가 모이며 소비자에게 도움이 되는지를 확인합니다.

## 3. 사용자

- **소비자**: 로그인 없이 음식점을 검색하고 공개 리뷰와 항목별 평가 결과를 확인합니다.
- **일반 사용자**: 카카오 로그인 후 내 활동과 신고 기능을 사용하고 내 활동에서 라이더 인증번호를 입력할 수 있습니다.
- **리뷰 작성자**: `RIDER` 또는 `ADMIN` 역할로 리뷰를 작성·수정하고 자신의 활성 리뷰를 관리합니다.
- **관리자**: 신고를 검토하고 잘못된 음식점 정보를 정정합니다.

## 4. 꼭 지켜야 할 신뢰 원칙

카카오 로그인은 같은 사용자를 구분하고, 공용 인증번호는 Rider Voice 안에서 리뷰를 작성할 수 있는 `RIDER` 역할을 부여합니다. 번호 보유나 작성자 5명 기준을 리뷰 내용의 사실성 또는 조작 방지 보장으로 표현하지 않습니다. 공개 API와 화면에는 방문 인증 상태나 인증 배지를 제공하지 않습니다.

## 5. 주요 사용 흐름

### 5.1 음식점 검색

1. 소비자가 음식점명이나 주소를 검색합니다.
2. 서비스에 등록된 음식점과 카카오 검색 결과를 함께 보여줍니다.
3. 아직 리뷰가 없는 음식점도 리뷰가 없다는 상태와 함께 보여줍니다.
4. 카카오 검색을 사용할 수 없으면 등록된 음식점만 보여주고 검색이 제한되었음을 알립니다.

### 5.2 로그인과 리뷰 작성

1. 사용자는 로그인할 때마다 카카오 계정을 다시 인증해 원하는 계정으로 로그인합니다.
2. 로그인 화면에서 카카오 로그인은 계정 식별이며 리뷰 작성에는 `RIDER` 또는 `ADMIN` 역할이 필요하다는 안내를 확인합니다.
3. 로그인 성공 후 앱 딥링크로 받은 일회용 코드를 Rider Voice token으로 교환합니다.
4. access token은 앱 메모리, refresh token은 SecureStore에 보관하고 갱신할 때마다 회전합니다.
5. 기본 `USER`는 내 활동에서 공용 6자리 인증번호를 입력해 `RIDER` 역할을 얻습니다.
6. `RIDER` 또는 `ADMIN`은 음식점, 방문 연월과 6개 평가 항목을 선택합니다.
7. 필요한 경우 200자 이내의 자유 의견을 작성하며 정해진 평가와 의견은 작성 직후 공개됩니다.

### 5.3 카카오에 없는 배달 브랜드 등록

작성자는 카카오 검색에 없는 브랜드도 다음 방법으로 등록하면서 첫 리뷰를 작성할 수 있습니다.

- 이미 등록된 픽업 장소에 새 배달 브랜드를 추가합니다.
- 주소 검색으로 실제 픽업 장소를 확인하고 새 배달 브랜드를 등록합니다.

모바일 앱에서는 다음 순서로 진행합니다.

1. `RIDER` 또는 `ADMIN` 역할로 로그인한 상태에서 수동 등록 흐름에 진입합니다.
2. 주소를 검색하고 카카오가 반환한 표준 주소 후보를 선택합니다.
3. 배달 브랜드명, 선택적인 상세 위치와 이용 중인 배달 플랫폼을 입력합니다.
4. 6개 평가와 방문 연월을 작성해 첫 리뷰를 제출합니다.

선택한 주소가 이미 Rider Voice의 픽업 장소라면 그 장소에 브랜드만 추가합니다. 새로운 주소라면 픽업 장소와 브랜드를 함께 만듭니다. 두 경우 모두 음식점 정보만 따로 저장하지 않고 첫 리뷰와 같은 트랜잭션에서 생성합니다.

사용자가 입력한 주소와 장소 정보는 그대로 믿지 않고 검색 결과를 다시 확인합니다. 음식점 등록에 실패하면 첫 리뷰도 등록되지 않습니다. 최초 등록자에게 음식점 소유권이나 수정 권한을 주지는 않습니다.

카카오 검색으로 등록한 음식점은 카카오 장소 ID를 음식점에 함께 저장해 같은 카카오 장소가 중복 등록되는 것을 막습니다. 주소로 수동 등록한 음식점에는 카카오 장소 ID가 없을 수 있습니다.

### 5.4 공개와 관리

- 브랜드와 픽업 장소의 평가 결과는 각각 서로 다른 작성자 5명부터 공개합니다.
- 5명 미만일 때는 결과 대신 현재 리뷰를 작성한 사람 수를 보여줍니다.
- 유효한 작성자가 다시 5명 미만이 되면 평가 결과도 다시 숨깁니다.
- 자유 의견을 수정하면 수정 내용이 즉시 공개됩니다. 단, 신고로 숨겨진 의견은 신고 처리 전까지 계속 숨깁니다.
- 신고가 접수되면 확인이 끝날 때까지 공개 의견만 숨기고 정해진 평가는 유지합니다.
- 문제가 의견에만 있으면 의견만 숨기고, 허위 작성이나 반복 도배라면 리뷰 전체를 공개와 집계에서 제외합니다.
- 관리자는 잘못된 이름, 픽업 장소와 폐업 정보를 정정하고 변경 기록을 남깁니다.

## 6. 리뷰 작성과 평가 규칙

- `RIDER`와 `ADMIN`만 리뷰를 생성·수정할 수 있습니다.
- `USER`, `RIDER`, `ADMIN`은 자신의 리뷰를 조회·삭제할 수 있습니다.
- 한 사용자는 같은 음식점에 활성 리뷰를 하나만 가질 수 있습니다.
- 활성 리뷰가 있다면 새 리뷰 대신 기존 리뷰를 수정해야 합니다.
- 방문 연월은 이번 달 또는 지난달만 선택할 수 있으며 작성 후 바꿀 수 없습니다.
- 활성 리뷰만 수정하거나 삭제할 수 있고, 다른 사람의 리뷰나 비활성 리뷰는 수정·삭제할 수 없습니다.
- 삭제는 기록을 남기는 방식으로 처리하며 삭제된 리뷰는 사용자에게 보여주지 않습니다.
- 삭제되거나 전체 제외된 뒤에는 최초 작성일로부터 90일이 지나야 다시 작성할 수 있습니다.
- 삭제·전체 제외 리뷰도 계정당 최근 24시간 최대 10개의 작성 횟수에 포함합니다.

평가 항목은 다음 6개입니다.

| 구분 | 평가 항목 |
| --- | --- |
| 배달 브랜드 | 포장 안정성, 주문 준비 상태, 주문 확인과 전달 정확성 |
| 픽업 장소 | 픽업 공간 청결, 직원 응대, 라이더 존중 |

6개 항목은 모두 작성하며 `매우 좋음`, `좋음`, `개선 필요`, `큰 개선 필요`, `관찰하지 못함` 중 하나를 선택합니다. `관찰하지 못함`은 선택한 사람 수로는 보여주지만 평가 비율에서는 제외합니다.

한 작성자가 같은 픽업 장소의 여러 브랜드에 리뷰를 남긴 경우, 픽업 장소 결과에는 가장 최근의 유효한 리뷰 하나만 반영합니다.

## 7. MVP 범위

이 장은 현재 제공하는 기능과 아직 제공하지 않는 기능을 구분합니다. 서버·배포 관련 항목은 사용자가 직접 보는 기능은 아니지만 서비스를 안전하게 운영하기 위한 내부 범위입니다.

### 이번에 포함하는 것

- Expo와 React Native 기반 iOS·Android 개발 빌드(`com.ridervoice.app`)의 홈, 음식점 검색, 상세 조회, 카카오 로그인, 리뷰 작성·수정·삭제와 내 활동 흐름
- 모바일 앱에서 Spring Boot `/api/v1`만 호출하는 API 연결 계층과 로딩·오류·빈 상태
- `ridervoice://auth/callback`으로 전달하는 2분 유효·일회용 교환 코드 기반 모바일 로그인. 서비스 token은 딥링크에 넣지 않고 access token은 메모리, refresh token은 SecureStore에 보관
- 카카오 로그인
- 공용 6자리 인증번호와 `USER`·`RIDER`·`ADMIN` 역할 기반 작성 권한
- 로그인 없는 음식점 검색, 상세 정보와 공개 리뷰 조회
- 실제 픽업 장소와 소비자에게 보이는 배달 브랜드의 분리
- 카카오 장소 및 주소 검색을 이용한 음식점 등록
- 모바일 주소 검색, 기존 픽업 장소 재사용과 새 장소 등록을 포함한 네 가지 리뷰 대상 작성 흐름
- 6개 평가 항목, 방문 연월과 200자 이내의 자유 의견
- 음식점별 활성 리뷰 1개와 90일 재작성 제한
- 작성자 5명부터 공개하는 브랜드 및 픽업 장소 평가 결과
- 공개되는 6개 평가 항목별 응답을 1.0~5.0으로 동일 간격 환산한 점수. 음식점 종합 점수, 평균 별점, 순위는 만들지 않음
- 자유 의견 신고와 사후 조치, 음식점 이름·픽업 장소·폐업 정보 정정
- master 대상 PR의 백엔드 전체 검증과 병합 후 Docker Hub 게시 자동화
- 운영 DB 목표인 RDS MySQL 8.4.10과 동일한 버전의 CI 통합 검증
- Flyway versioned migration과 Hibernate schema validation을 이용한 운영 DB 변경 검증
- 기존 Ubuntu EC2 한 대와 비공개 RDS MySQL을 사용하는 백엔드 운영 배포
- GitHub OIDC와 SSM Run Command를 이용한 master 이미지 자동 배포 및 컨테이너 rollback
- Elastic IP 기반 `sslip.io` 임시 주소, Nginx와 Let's Encrypt를 이용한 HTTPS
- Spring Boot Actuator와 Micrometer 기반 로컬·CI 메트릭
- 로컬 Spring 프로세스를 수집하는 개발용 Prometheus·Grafana Compose 구성

### 이번에 포함하지 않는 것

- React 웹 frontend와 refresh cookie 기반 브라우저 로그인 API
- 방문 인증 상태, 공개 인증 배지와 인증번호 개별 발급 기능
- 사용자 위치 권한, 거리 표시와 가까운 순 정렬
- Expo Go와 Expo Web에서의 실제 로그인·리뷰 변경. Expo Go는 API가 설정된 공개 조회와 UI 확인에만 사용
- 모바일 앱 스토어 배포와 관리자 화면 배포
- Redis, Kafka, Elasticsearch 같은 추가 인프라
- 전체 애플리케이션용 Docker Compose, ALB, ECS, Route 53, NAT Gateway와 다중 API 인스턴스
- 운영 EC2에서 실행하는 Prometheus·Grafana와 공개 `/grafana/` 대시보드
- Alertmanager, 로그·트레이스 수집과 고가용성 모니터링

## 8. 완료 기준

- 소비자가 로그인 없이 음식점을 검색하고 공개 리뷰를 볼 수 있어야 합니다.
- `RIDER`와 `ADMIN` 사용자가 기존 음식점 또는 확인된 장소에 리뷰를 작성·수정할 수 있고 `USER`는 작성할 수 없어야 합니다.
- 같은 음식점의 활성 리뷰 중복과 삭제·전체 제외를 이용한 90일 제한 우회를 막아야 합니다.
- 정해진 평가와 자유 의견은 작성·수정 즉시 공개되어야 합니다.
- 브랜드와 픽업 장소의 결과가 각각 작성자 5명 기준에 맞게 공개되어야 합니다.
- `관찰하지 못함`이 평가 비율에서 제외되어야 합니다.
- 신고된 의견과 리뷰, 잘못된 음식점 정보를 관리자가 처리할 수 있어야 합니다.
- 공개 리뷰와 평가 결과에는 방문 인증 상태나 인증 안내 필드가 없어야 합니다.
- master 대상 PR에서 백엔드·MySQL 통합 테스트와 컨테이너 기동 검증이 성공해야 병합할 수 있으며, 병합된 백엔드 이미지만 Docker Hub에 게시되어야 합니다.
- MySQL 통합 검증은 운영 RDS 목표 버전인 MySQL 8.4.10을 사용해야 합니다.
- 완전히 빈 MySQL에 Flyway migration을 적용한 뒤 Entity, FK, unique와 index가 일치해야 합니다.
- master 이미지가 Docker Hub에 게시되면 GitHub가 장기 AWS access key 없이 OIDC로 배포 권한을 얻어 지정 EC2에 자동 배포해야 합니다. 배포는 같은 master commit의 backend script와 Nginx 설정을 사용해야 합니다.
- 운영 API는 Nginx 뒤의 localhost Docker container로만 실행되고 HTTPS health check를 통과해야 하며, 새 container가 정상화되지 않으면 이전 이미지로 복구해야 합니다.
- RDS는 외부에 공개하지 않고 EC2에서 TLS host 검증을 거쳐 runtime·migration 분리 계정으로 연결해야 합니다.
- 로컬 Prometheus는 개발 API 메트릭을 수집하고 Grafana 대시보드에서 API 상태, HTTP 요청, JVM과 DB connection pool 상태를 확인할 수 있어야 합니다.
- 운영 EC2에는 Prometheus·Grafana container와 volume을 유지하지 않고 외부 metric endpoint, `/grafana`와 `/grafana/`를 `404`로 차단해야 합니다.
