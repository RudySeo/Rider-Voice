# Rider Voice 문서 안내

이 폴더는 Rider Voice가 **왜 필요한지**, **어떻게 사용하는지**, **어떤 기준으로 만들었는지**를 설명합니다. 기획·운영 담당자는 이 문서부터 읽고, 필요한 경우 연결된 기술 문서를 확인하면 됩니다.

## 1분 요약

Rider Voice는 음식점의 맛이나 일반 고객 응대가 아니라 다음과 같은 **배달 준비와 픽업 경험**을 공유하는 서비스입니다.

- 포장이 안정적인지
- 주문이 제때 준비되는지
- 주문 확인과 전달이 정확한지
- 픽업 공간이 깨끗한지
- 직원 응대가 원활한지
- 배달 업무 종사자를 존중하는지

소비자는 로그인 없이 음식점을 검색하고 공개 리뷰를 확인할 수 있습니다. 카카오 로그인 신규 사용자는 `USER`이며, 운영자가 관리하는 6자리 공유 인증번호로 `RIDER` 권한을 얻은 뒤 리뷰를 작성할 수 있습니다. 이 권한은 서비스 내부 작성 권한이며 공개 신원·방문 인증으로 표시하지 않습니다.

## 서비스가 동작하는 모습

```text
소비자 또는 리뷰 작성자
          │
          ▼
    Rider Voice 앱
          │
          ▼
      API 서버
      ├── 사용자와 로그인 관리
      ├── 음식점 검색과 등록
      ├── 리뷰 규칙과 공개 처리
      └── 신고와 관리자 처리
          │
          ├── Rider Voice 데이터베이스
          └── 카카오 로그인·장소 검색
```

앱은 데이터베이스나 카카오를 직접 호출하지 않습니다. 서버가 검색 결과와 사용자 입력을 다시 확인하고 모든 주요 규칙을 적용합니다.

## 핵심 용어

| 용어 | 쉬운 설명 | 예시 |
| --- | --- | --- |
| 픽업 장소 | 음식을 실제로 가져가는 물리적인 장소 | 행복공유주방 강남점 |
| 배달 브랜드 | 소비자가 배달 앱에서 보는 음식점 이름 | 강남 떡볶이 |
| 활성 리뷰 | 현재 공개와 집계에 사용할 수 있는 사용자의 최신 리뷰 | 삭제·전체 제외되지 않은 리뷰 |
| 라이더 권한 | 공유 인증번호로 부여하는 내부 리뷰 작성 권한 | `RIDER` |
| 구조화 평가 | 정해진 6개 질문에 선택지로 답한 평가 | 포장 안정성 `좋음` |
| 자유 의견 | 선택적으로 작성하는 200자 이내 문장 | 픽업 위치가 조금 좁았어요 |
| 집계 결과 | 여러 작성자의 평가를 항목별로 모은 결과 | 포장 안정성 응답 분포 |

한 픽업 장소에서 여러 배달 브랜드를 운영할 수 있습니다. 서비스 내부에서는 이 관계를 구분하지만, 같은 장소의 다른 브랜드 목록은 소비자에게 공개하지 않습니다.

## 꼭 알아야 할 운영 규칙

- 개별 구조화 평가와 자유 의견은 작성·수정 직후 공개됩니다.
- 브랜드와 픽업 장소의 집계 결과는 각각 서로 다른 유효 작성자 5명부터 공개됩니다.
- 한 사용자는 음식점마다 활성 리뷰를 하나만 가질 수 있습니다.
- 리뷰 생성·수정은 `RIDER`와 `ADMIN`만 할 수 있고 조회·삭제·신고는 모든 로그인 사용자가 할 수 있습니다.
- 리뷰를 삭제하거나 전체 제외하면 최초 작성일부터 90일 후 다시 작성할 수 있습니다.
- 신고가 접수되면 자유 의견만 우선 숨기고 구조화 평가는 유지합니다.
- 종합 점수, 평균 별점, 음식점 순위와 인증 배지는 제공하지 않습니다.
- 이미지 업로드, 배달 내역 캡처, OCR과 방문 인증은 현재 범위가 아닙니다.

## 현재 구현과 후속 범위

현재 MVP에는 공개 검색·상세·리뷰, 카카오 로그인, 네 가지 리뷰 작성 대상, 내 리뷰 관리, 신고와 관리자 처리가 포함되어 있습니다. 모바일 앱은 iOS·Android 개발 빌드를 기준으로 하며 백엔드는 단일 API 서버와 MySQL을 사용합니다.

관리자 전용 모바일 화면, 앱스토어 배포, 실제 라이더·방문 인증, 거리 기반 검색과 대규모 분산 인프라는 후속 검토 항목입니다. 문서에서 `후속`, `제외`, `폐기됨`으로 표시한 내용은 현재 동작으로 해석하지 않습니다.

## 문서 변경 원칙

- 제품 범위가 바뀌면 코드보다 문서를 먼저 수정합니다.
- API 요청과 응답의 최종 기준은 실행 중인 OpenAPI 문서입니다.
- 데이터베이스 구조의 최종 기준은 JPA Entity와 Flyway migration입니다.
- 문서끼리 표현이 다르면 신뢰 원칙과 현재 구현을 우선 확인하고 관련 문서를 함께 수정합니다.
