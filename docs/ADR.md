# Rider Voice Architecture Decision Records

## 철학

Rider Voice는 빠른 화면 구현보다 검증 가능한 방문 데이터와 안전한 운영 정책을 우선한다. 서버가 모든 업무 규칙의 기준이 되며, 개인정보를 최소한으로 보관하고 자동 판정이 불확실한 경우 관리자 검수로 안전하게 전환한다.

---

### ADR-001: 서버 API 우선 개발

**결정**: Spring Boot 서버 API와 OpenAPI 계약을 완성한 후 React Native 앱을 개발한다.

**이유**: 인증, OCR, 글쓰기 권한, 집계와 검수 규칙이 제품 신뢰의 핵심이다. 서버 계약을 먼저 안정화하면 iOS와 Android가 동일한 규칙을 사용할 수 있고 화면 개발 중 API가 반복 변경되는 비용을 줄일 수 있다.

**트레이드오프**: 초기에는 사용자가 직접 체험할 수 있는 화면이 늦게 나온다. 이를 보완하기 위해 OpenAPI UI와 서버 통합 테스트로 전체 흐름을 먼저 검증한다.

### ADR-002: Spring Boot와 Kotlin 선택

**결정**: API 서버는 Spring Boot와 Kotlin으로 구현한다.

**이유**: Spring Security, Validation, Transaction, JPA 등 서버 애플리케이션에 필요한 기반이 성숙해 있으며 Kotlin의 null safety와 간결한 문법을 활용할 수 있다.

**트레이드오프**: Kotlin과 JPA proxy의 궁합을 고려해 entity를 open 처리하거나 Kotlin JPA plugin을 사용해야 하며, entity의 불변성을 일반 Kotlin 객체처럼 적용하기 어렵다.

### ADR-003: PostgreSQL, JPA와 Flyway 선택

**상태**: ADR-013으로 대체됨.

**결정**: 영속 데이터는 PostgreSQL에 저장하고 Spring Data JPA/Hibernate로 접근하며 모든 스키마 변경은 Flyway로 관리한다.

**이유**: 사용자, 방문, 리뷰, 검수와 집계 데이터 사이의 관계와 트랜잭션 무결성이 중요하다. PostgreSQL은 관계형 제약, 인덱스와 집계에 적합하고 JPA는 도메인 중심 CRUD 구현을 단순화한다.

**트레이드오프**: 복잡한 집계는 JPA만으로 비효율적일 수 있다. 리포트 조회에는 projection과 명시적 query를 허용하고 snapshot 테이블을 사용한다.

### ADR-004: REST와 OpenAPI를 클라이언트 계약으로 사용

**결정**: JSON REST API를 제공하고 OpenAPI 문서를 계약의 기준으로 사용한다.

**이유**: React Native 개발 전에 서버 요청·응답과 오류 모델을 검증할 수 있고, 이후 TypeScript 타입과 API client를 생성할 수 있다.

**트레이드오프**: API 변경 시 문서와 생성 client의 호환성을 관리해야 한다. CI에서 OpenAPI schema 변경을 검증한다.

### ADR-005: 카카오 공개 가입과 방문별 검증

**결정**: 누구나 카카오 계정으로 가입할 수 있고 별도의 라이더 자격 심사를 하지 않는다. 각 리뷰는 배달 완료 증빙으로 방문을 검증한다.

**이유**: 계정 단위의 2차 심사는 가입 장벽과 관리자 운영 비용을 높인다. 제품에 필요한 핵심 신뢰는 사용자의 직업 신분보다 리뷰 대상 음식점을 실제 배달 과정에서 방문했다는 사실이다.

**트레이드오프**: 소셜 로그인만으로 라이더 자격을 보증할 수 없다. 공개 문구를 `방문 인증 리뷰`로 제한하고 중복·조작 탐지를 강화한다.

### ADR-006: 방문별 1회용 글쓰기 권한

**결정**: 방문이 승인되면 사용자와 음식점에 귀속된 24시간 유효 WriteGrant를 발급하고 리뷰 제출 시 원자적으로 소진한다.

**이유**: 회원이 임의의 음식점을 선택해 글을 작성하거나 하나의 증빙을 여러 리뷰에 재사용하는 것을 도메인 수준에서 방지할 수 있다.

**트레이드오프**: 리뷰 작성 도중 권한이 만료될 수 있고 동시 제출을 고려한 잠금이 필요하다. 만료 시간을 화면에 노출하고 조건부 갱신으로 한 요청만 성공시킨다.

### ADR-007: CLOVA OCR과 배민 파서 우선

**상태**: ADR-017로 대체됨.

**결정**: NAVER Cloud CLOVA OCR로 텍스트를 추출하고 배달의민족 완료 화면 전용 parser를 먼저 구현한다. 다른 앱은 수동 검수로 처리한다.

**이유**: 한국어 화면 인식과 배달 앱별 구조 해석을 분리할 수 있으며 단일 앱에 집중해 자동 판정 정확도를 먼저 측정할 수 있다.

**트레이드오프**: 파일럿 초기에는 다른 배달 앱의 자동 승인이 불가능하고 운영자의 수동 검수 부담이 발생한다.

### ADR-008: 카카오 장소 ID를 음식점 기준 식별자로 사용

**결정**: 카카오 로컬 API의 장소 ID, 이름, 주소와 좌표를 내부 Restaurant에 연결한다.

**이유**: OCR의 음식점 문자열만으로는 동명 지점과 주소 변경을 안정적으로 구분하기 어렵다. 외부 장소 ID를 사용하면 검색 결과와 리포트 대상을 일관되게 연결할 수 있다.

**트레이드오프**: 카카오 장소 데이터 변경과 API 장애에 영향을 받는다. 내부 캐시와 마지막 동기화 정보를 저장하고 운영자가 잘못된 연결을 수정할 수 있게 한다.

### ADR-009: AWS 비공개 증빙 처리

**상태**: 후속 운영 단계의 결정이며 현재 로컬 개발 단계에서는 구현하지 않음.

**결정**: 증빙은 public access가 차단된 S3에 업로드하고 SQS worker가 처리한다. OCR 성공 원본은 즉시, 수동 검수 원본은 최대 72시간 후 삭제한다.

**이유**: API 서버를 통한 대용량 파일 중계를 피하면서도 접근 권한과 보존 기간을 통제할 수 있다. 비동기 큐는 외부 OCR 지연과 장애를 사용자 요청에서 분리한다.

**트레이드오프**: S3, SQS, worker, lifecycle과 재시도 운영이 필요하다. DLQ와 삭제 모니터링을 필수로 구성한다.

### ADR-010: 구조화 리뷰와 최소 표본 공개

**결정**: 직접 관찰 가능한 6개 항목을 구조화해 수집하고 최근 90일 내 서로 다른 작성자 5명부터 리포트를 공개한다.

**이유**: 단일 작성자의 감정과 종합 별점보다 반복 관찰된 항목별 분포가 서비스 목적에 맞는다. 최소 표본은 한 사람의 평가가 음식점에 과도한 영향을 주는 것을 줄인다.

**트레이드오프**: 파일럿 초기에 공개할 수 있는 음식점이 적다. 반경 3km에 데이터를 집중하고 공개 전에는 `데이터 수집 중` 상태를 제공한다.

### ADR-011: 자유 의견은 관리자 승인 후 공개

**결정**: 자유 의견은 규칙 기반 개인정보·금지 표현 탐지를 거치고 관리자가 승인한 후 공개한다.

**이유**: 개인정보, 명예훼손 가능성이 있는 단정, 혐오 표현이 공개된 뒤 대응하는 것보다 사전 검수가 안전하다.

**트레이드오프**: 실시간 공개가 아니며 관리자 운영 비용이 발생한다. 선택형 데이터는 자유 의견과 분리해 집계할 수 있게 한다.

### ADR-012: React Native 크로스 플랫폼 클라이언트

**결정**: 서버 API 완료 후 iOS와 Android 클라이언트를 React Native로 구현한다.

**이유**: 하나의 TypeScript 코드베이스에서 두 모바일 플랫폼을 지원할 수 있고 카메라·이미지 업로드 중심 사용자 경험을 제공할 수 있다.

**트레이드오프**: 네이티브 모듈과 빌드 설정에서 플랫폼별 작업이 남는다. Expo와 Bare 방식은 OCR 업로드, 소셜 로그인, 배포 요구사항을 검토한 뒤 별도 ADR에서 결정한다.

### ADR-013: MySQL, JPA와 Flyway로 전환

**결정**: 영속 데이터베이스를 PostgreSQL에서 MySQL로 전환한다. 로컬과 통합 테스트는 MySQL 9.3을 기준으로 하며, Spring Data JPA/Hibernate와 Flyway를 계속 사용한다.

**이유**: 현재 로컬 개발 환경의 데이터베이스를 MySQL로 통일해 애플리케이션과 데이터베이스 간 호환성을 직접 검증한다. 사용자, 방문, 리뷰와 검수 데이터에 필요한 관계형 제약과 트랜잭션은 MySQL InnoDB로 유지할 수 있다.

**트레이드오프**: PostgreSQL의 `UUID`, `TIMESTAMPTZ`, 부분 인덱스 같은 기능을 직접 사용할 수 없다. UUID는 `BINARY(16)`, 시각은 UTC `DATETIME(6)`, 활성 레코드 조회 인덱스는 복합 인덱스로 표현하고 로컬 MySQL에서 호환성을 검증한다. 기존 PostgreSQL 데이터는 이관하지 않는다.

### ADR-014: 현재 개발은 로컬 실행만 사용

**결정**: 현재 단계에서는 Spring Boot API와 MySQL을 로컬 프로세스로 직접 실행한다. Docker, Docker Compose, Testcontainers, AWS 배포와 production readiness 작업은 사용자가 별도로 요청하기 전까지 수행하지 않는다.

**이유**: 서버 API와 데이터 모델을 빠르게 검증하는 현재 단계에서는 로컬 실행 환경으로 충분하며, 컨테이너와 배포 인프라 운영 비용을 미리 도입하지 않는다.

**트레이드오프**: 개발자별 로컬 환경 차이를 자동으로 격리하지 못하고 CI와 운영 환경의 재현성 검증이 미뤄진다. 해당 검증은 배포 착수가 명시된 후 별도 계획과 ADR로 보완한다.

### ADR-015: 약관 동의 전용 온보딩 토큰

**결정**: 약관에 동의하지 않은 신규 사용자의 카카오 callback에는 짧은 수명의 일회용 온보딩 토큰을 발급한다. 이 토큰은 약관 동의 API에만 사용할 수 있으며 동의 완료 후 정식 access token과 rotating refresh token으로 교환한다.

**이유**: 신규 사용자가 정식 세션 없이도 본인 callback 흐름을 이어 약관에 동의할 수 있어야 한다. `PENDING_TERMS` 사용자에게 일반 access token을 발급하는 것보다 허용 범위를 명확히 제한할 수 있다.

**트레이드오프**: 별도의 토큰 종류, 만료와 일회성 소비 검증이 필요하다. 온보딩 토큰으로 다른 사용자 API를 호출할 수 없는지 보안 테스트를 유지한다.

### ADR-016: 방문 인증 전 비공개 리뷰 초안

**결정**: 필수 약관에 동의한 로그인 사용자는 음식점을 선택해 `ReviewDraft`를 저장하고 수정할 수 있다. 초안은 정식 `Review`와 분리하며 공개, 리포트 집계, 기여 지표와 관리자 검수에 포함하지 않는다. 정식 리뷰는 향후 유효한 `WriteGrant`와 본인 소유 초안을 하나의 트랜잭션에서 전환할 때만 생성한다.

**이유**: OCR 방문 인증 구현을 기다리지 않고 로그인과 리뷰 작성 경험을 먼저 검증하면서도, 방문 인증 리뷰라는 제품의 핵심 신뢰 규칙을 유지할 수 있다.

**트레이드오프**: 초안과 정식 리뷰의 수명 주기 및 변환 경계를 별도로 관리해야 한다. 방문 인증을 완료하지 않은 초안은 영구적으로 공개되거나 집계될 수 없다.

### ADR-017: OCR 공급자와 LangChain 구성 결정 연기

**결정**: 방문 증빙 자동 추출은 로그인, 음식점 검색과 리뷰 초안 이후에 구현한다. OCR 단계 착수 시 NAVER Cloud CLOVA OCR과 멀티모달 모델을 정확도, 비용과 운영 복잡도 기준으로 비교하고, LangChain4j를 Spring Boot 내부에 둘지 Python LangChain 서비스를 분리할지 함께 결정한다. 선택 결과는 구현 전에 후속 ADR로 기록한다.

**이유**: 현재 우선 목표에는 자동 OCR이 필요하지 않으며 공급자와 framework를 미리 고정하면 검증되지 않은 운영 복잡도가 핵심 사용자 흐름 개발을 지연시킨다.

**트레이드오프**: 방문 인증 자동화와 정식 리뷰 전환이 늦어진다. 그 전까지 작성물은 비공개 초안으로만 유지하며 OCR application port는 특정 provider 타입에 의존하지 않게 설계한다.
